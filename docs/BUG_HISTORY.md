# Bug history

One entry per fixed bug. Every fix starts with a failing test (§11).

| Date | Symptom | Root cause | Fix | Test |
|---|---|---|---|---|
| 2026-11-14 | Bootstrap placeholder `.gitkeep` was pulled into the vault after syncing against an empty repo. | Remote tree walk applied no exclusion rules; only the local scan did. | Excluder passed to the remote walk (files invisible, excluded dirs not fetched); root `.gitkeep` added to the hard excludes. | `sync.test.ts` "edits, deletes and renames flow between devices"; `remote-diff.test.ts` "excluded files are invisible" |
| 2026-11-14 | Every pulled file was re-read and re-hashed on the following scan. | Orchestrator dropped pulled paths from the mtime/size cache instead of recording what it had just written. | `applyPull` stats each written file and returns `cacheUpdates`; orchestrator merges them into the cache. | `sync.test.ts` "second scan reads nothing when files are unchanged" |
| 2026-11-14 | Property test: device B saw an empty repo, device A bootstrapped and pushed in between, B bootstrapped and the remote lost As commit. | Fake `bootstrapRepo` rewrote the ref with a new root commit; port contract did not forbid it. Real Contents API commits on top of an existing branch. | Port contract now requires `bootstrapRepo` to be harmless on an existing branch; fake adds `.gitkeep` on top or returns the head. Adapter (milestone 6) must honour this. | `property.test.ts` "converges without losing data" (race fault) |
| 2026-11-15 | Property test: after a partial pull, a later remote revert to an earlier tree left a stale file on one device forever; both devices then reported "noop" while differing. | `baseline.files` was updated per file while `baseline.dirs` kept the old tree sha. Git trees can return to an earlier sha, so the walk skipped the root as "unchanged" and copied the stale file list. | All baseline file mutations go through `core/baseline.ts`, which drops the cached sha of every ancestor directory; a clean sync re-records them. | `sync.test.ts` "a remote tree that returns to an earlier shape after a partial sync is still re-walked (regression)"; `property.test.ts` |
| 2026-11-18 | A note the user re-created after the scan (deleted locally, edited remotely) could be overwritten by the resurrected remote version. | The edited-during-sync check in `applyPull` ran only for `pull`, not `resurrect`. | The check runs for every write; a file that appeared since the scan counts as edited. | `apply.test.ts` "a resurrect does not overwrite a file the user re-created after the scan (regression)" |
| 2026-11-18 | A remote rename could land on (and replace) a note the user had just created at the target path. | The rename only re-checked its source path, never the target. | Both source and target are re-checked; the rename is skipped and retried next sync. | `apply.test.ts` "a remote rename does not land on a file the user created at the target after the scan (regression)" |
| 2026-11-18 | (Adapter, caught before release) A new note or rename target inside a folder stored with an NFD name (iOS/macOS) was created under the NFC spelling, making a duplicate folder on normalization-sensitive filesystems. | `ObsidianVault` mapped only already-listed files back to their on-disk names, not the folder of a file about to be created. | Unknown paths resolve their parent folder to its on-disk spelling; same for rename targets. | `obsidian-vault.test.ts` "NFD names on disk are found by their NFC key for read, write, stat and delete" |
| 2026-11-18 | (Test harness) Property test through the adapter reported "b0.bin disappeared although no user deleted it". | Harness defect, not a sync bug: device B deleted content X, device A then rewrote the same bytes X (A→B→A). Content-based 3-way sync, like git, correctly applies B's delete. The harness treated A's identical rewrite as un-deleting the path. | Harness tracks deleted binary content per path; an identical rewrite no longer cancels the deletion. | `property.test.ts` "converges without losing data through the real GitHub adapter" (seed 20261118) |
| 2026-11-18 | (Design, caught before first use) Polling could have skipped an unsynced remote change forever, and a deleted branch looked like "no change". | `getRefIfChanged` returned `null` for both 304 and a missing branch, and only the ETag was stored, not the head it belongs to; a poll seeing a new head followed by a failed sync would get 304 next time. | Port returns `unchanged` / `changed` / `missing`; `{sha, etag}` stored together; `checkRemote` compares the polled head with `baseline.remoteHead`. | `scheduler.test.ts` "a change seen by a poll stays 'changed' (via 304) until a sync actually succeeds" |
| 2026-11-18 | Dot-files in the repo outside the config dir (`.github/workflows/*`, `.editorconfig`, `.gitignore`) were pulled into the vault and, on the next sync, deleted from GitHub. | The excluder and the vault listing disagreed: core only hid the config dir, but `ObsidianVault` cannot see any dot-path it is not told about, so the scan reported those files as locally deleted and pushed the deletion. | One rule in `buildExcluder`: dot-paths outside the config dir are excluded (they stay untouched on GitHub), except files in `LISTED_HIDDEN_FILES` (`.gitignore`), which `ObsidianVault` now always lists from the same constant. Previously synced dot-files drop out of the baseline without any deletion. | `obsidian-vault.test.ts` "a .github/ workflow in the repo is never deleted by syncing through the Obsidian adapter" |
